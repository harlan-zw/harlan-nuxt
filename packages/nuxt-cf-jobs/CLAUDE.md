# nuxt-cf-jobs

Nuxt module for typed Cloudflare Queue jobs. Scans `server/jobs`, generates a typed registry, exposes runtime helpers for sending/consuming queue messages and persisting durable jobs in D1.

## Downstream consumers

Both linked via `link:../../pkg/nuxt-cf-jobs` (or deeper). Changes here ship to them immediately, so check both before deleting or renaming public surface.

### `~/sites/gscdump.com`

- Single Nuxt app. `cfJobs.queues` = `sync-critical`, `sync-standard`, `sync-extended`, `webhook`.
- Heavy user of the **durable / outbox** path. Pulls these directly from `#cf-jobs/server`:
  - `claimDurableJob`, `completeDurableJob`, `failDurableJob`, `releaseDurableJob`
  - `dispatchRegisteredJob`, `dispatchDurableJobBatch`, `dispatchDurableJobContinuations`
  - `prepareDurableJob`, `enqueueDurableJob`
  - `getDurableJobContinuationsForStage`, `parseDurableJobContinuation`, `serializeDurableJobContinuation`
  - `createQueuePublisher`, `resolveQueueBindingName`, `resolveJobRetryDelay`, `resolveJobMaxAttempts`
- Imports the drizzle table defs from the **`nuxt-cf-jobs/schema`** subpath in `database/main/schema.ts` (a drizzle-kit context where the `#cf-jobs/*` nuxt alias doesn't resolve and pulling `./server` would drag `nitropack/runtime`).
- Also uses `#cf-jobs/app` (`jobRegistry`, `jobs`, `JobName`, `JobPayload`).
- Passes `cfJobs.defaultQueue` (supported in `ModuleOptions`).

### `~/sites/nuxtseo.com/apps/pro`

- Monorepo app composed of layers (`pro-dataforseo`, `pro-gsc`, `pro-indexing`, `pro-perf`, `pro-reports`, `pro-saas`, `pro-saas-billing`).
- Configures multi-`jobsDir` with paths into each layer — relies on `jobsDir: string[]` resolving relative to root.
- Queues: `billing`, `dataforseo`, plus more.
- Indirect consumers also at `~/sites/nuxtseo.com` (root vitest config).

## Implications for changes

- **The public surface is curated in `runtime/server/index.ts`, not `export *`.** The barrel re-exports the durable/outbox, d1, dispatch, errors, policy, registry, result, scheduled, schema and types modules wholesale (gscdump imports those lifecycle/dispatch helpers individually — don't delete/rename without grepping both sites).
- **Typed-error model (Effect-inspired, no dep): `errors.ts` + `result.ts`.** `errors.ts` is the `JobError` tagged union (`_tag`-discriminated: `no-task`, `handler-not-found`, `invalid-payload`, `payload-too-large`, `no-route`, `unknown-continuation`, `invalid-continuation`, `continuation-queue-mismatch`, `handler-threw`) with `jobErrors.*` constructors + `formatJobError` / `jobErrorToException` / `isJobError`. `result.ts` is the `Result<A,E>` = `Ok|Err` primitive (`ok`/`err`/`isOk`/`isErr`/`mapResult`/`mapErr`/`matchResult`/`unwrapResult`). `DispatchResult.error` is now a `JobError` (the old `handlerNotFound`/`invalidPayload`/`validationError` flags are gone — discriminate on `error._tag`; `error.cause` carries the old `validationError`). `prepareDurableJobResult` is the errors-as-values core (`prepareDurableJob` is the throwing wrapper over it); `validateDurableJobContinuations` returns `JobError | undefined` instead of throwing. `runDurableJobMessage`, `enqueueDurableJob` and `dispatchDurableJobBatch` now return discriminated unions (`RunDurableJobMessageResult` keyed on `status`, with a distinct `errored` for handler defects vs `released` for deliberate `ctx.release()`; `EnqueueDurableJobResult` = `enqueued | duplicate | not-dispatched | dispatch-failed`; `DispatchDurableJobBatchResult` per-queue = `sent | not-dispatched | failed{cause}`, also flowing through `SweepDurableJobsResult.dispatched` and `CreateJobBatchResult.dispatched`) instead of the old `{ status, error?: unknown }` / `{ inserted, dispatched, error? }` / `{ queue, dispatched, error? }` bags. **Breaking; downstream updated in lockstep:** gscdump's `job-consumer`/`job-dispatcher` (local `DispatchResult.error` retyped + `formatJobError`) and its `event-service.ts` batch-dispatch filter (`!r.dispatched` → `r.status !== 'sent'`, `r.error` → `r.cause`), plus nuxtseo-pro's `layers/saas/server/utils/cf-jobs-durable.ts` (`dispatch.error` → `formatJobError`). Both apps ignore `enqueueDurableJob`'s return (`.catch()` only), have no `runDurableJobMessage` consumers, and read only `batchId`/`jobIds` off `createJobBatch` (not `.dispatched`), so those reshapes needed no further app edits. Note in next release. `queue.ts` is the exception: only `resolveQueueBindingName`, `createJobQueue`, `defineCfJobsQueues`, `exponentialBackoff` and the `CF_QUEUE_MAX_*` constants are public; its transport/binding/DLQ/consumer helpers are module-private. `testing.ts` is **no longer** on the barrel — it ships on its own `#cf-jobs/testing` subpath (nitropack-free, test-only) so importing the harness never drags the barrel's `scheduled` → `nitropack/runtime` edge. `dev.ts`, `payload.ts`, `internal.ts` are internal-only. Tests of private helpers import them from the module path (`../src/runtime/server/queue`), not the barrel.
- **`exports` map = `.`, `./server`, `./outbox`, `./d1`, `./schema`, `./testing`.** `./server` (the curated umbrella) is the contract for in-nitro consumers. `./outbox` is the narrow framework-neutral transactional staging/publication surface for adapters. `./d1` and `./schema` exist for non-Nuxt contexts (Drizzle config, CLI migrations) where `#cf-jobs/*` aliases are unavailable. `./testing` carries the test harness and fake queues without Nitro runtime edges.
- **Publication state is explicit.** `prepareStageJobs` / `stagePreparedDurableJobs` insert unpublished rows, `publishDurableJobBatch` marks them published only after the Queue accepts them, and ordinary recovery selects unpublished rows by default. Orphan recovery may re-send published live rows only after the stale release, redelivery, and redispatch grace windows. `insertJob` / `insertJobs` remain legacy, immediately claimable inserts. Do not pair those legacy methods with manual dispatch when outbox recovery guarantees are required; migrate producers to stage + publish.
- **Terminal failure means terminal.** A job definition's `failed` callback runs after durable failure persistence, either for explicit `ctx.fail()` or after the stored attempt cap is exhausted. Per-attempt throws release with the stored backoff. Observer defects go to `onObserverError`, with `console.error` as the final fallback; they are never silently swallowed. Configure `reconcile.terminalFailureContext` when stale reaping must run `failed`; the generated adapter keeps application dependencies outside the package core.
- **`jobsDir` must keep supporting `string[]` with relative paths from app root** (nuxtseo layers). It now also accepts `true`, which discovers `server/jobs` in the app and every entry of `nuxt.options._layers`, the same rule as `tasksDir: true`. Both resolve through `resolveLayeredDirs` in `build/layers.ts`.
- **The orphan sweep is a producer, and two windows bound its write rate.** `reconcile.orphanedSeconds` (default 6h) decides which rows qualify; `reconcile.redispatchGraceSeconds` (defaults to `orphanedSeconds`) decides how often one row may be re-sent. The damping record is the `last_dispatched_at` + `dispatch_attempts` COLUMNS, not the `retry_reasons` evidence log: that log is capped at eight shared entries, so a busy row evicted its own marker and the sweep went memoryless. `findDispatchableJobs` reads the columns and keeps a row eligible when `last_dispatch_error` is set, so a failed send still retries next tick.
- **One reservation window.** `reconcile.staleSeconds` (default 900s) is the row's ownership window, and `createDurableRuntime` derives `reclaimAfterSeconds` from it through runtime config. An explicit `reclaimAfterSeconds` still wins. When the two drifted, reconcile released jobs the consumer still owned and terminalized the loser without settling its batch.
- **Generated templates that Nitro leaves outside its dev bundle must be inlined.** `build/nitro-dev.ts` `inlineTemplateInNitroDev` marks a buildDir template for Rollup in dev. Both the registry and `cf-jobs/reconcile-context.mjs` use it: without it Node's ESM loader reads the app source the proxy re-exports and every route errors. For the same reason the registry's lazy `import()` specifiers KEEP their source extension (`loadPath`); only the type positions are extensionless (`importPath`).
- **`defineJob({ maxAttempts })` is gone. Use `tries`.** The alias silently lost to `tries`. The build warns per file and `validateJobDefinitions` reports `removed-max-attempts` at boot.
- Auto-imports were narrowed to `defineJob` only — both consumers already use explicit imports from `#cf-jobs/server`, so this is safe.
- Build-time wrangler/queue reconciliation lives in `wrangler.ts` (`reconcileQueues`, `buildQueueExpectations`, `normalizeNitroQueues`, `mergeWranglerSources`); `module.ts` is thin wiring over it. Keep new merge/normalize/cross-check logic there so it stays unit-testable (`tests/wrangler-reconcile.test.ts`).
- **Tests run as two vitest `projects`** (`vitest.config.ts`): `unit` (happy-dom, all `tests/**/*.test.ts`, resolves runtime from source via `#cf-jobs/server` + `#cf-jobs/testing` aliases plus the `nitropack/runtime` stub) and `nitro` (`tests/**/*.nitro.test.ts`, node env, config in `tests/vitest.nitro.config.ts`). Nitro integration tests use `@nuxt/test-utils/e2e` `setup` + `$fetch` against `tests/fixtures/nuxt-demo` — the real Nuxt build under **nitropack v2** (do NOT use nitro-test-utils, which is nitro v3). Scripts: `test`/`test:unit` → unit, `test:nitro` → nitro, `test:e2e` → the wrangler/workerd round-trip tier (still the only thing that runs the real queue consumer).
